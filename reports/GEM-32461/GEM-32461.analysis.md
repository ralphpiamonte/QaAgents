Issue: GEM-32461 (Story)

1. Jira issue summary
GEM-32461 Story: Add invoice-linking controls (Add to Existing Invoice / Add to New Invoice) to the order screen footer (not cart), with mandatory-field gating, open-invoice visibility rules, redirect behavior, existing linking logic reuse, and eyeglasses makeability check (PV scope only).

2. Requirement/bug analysis
- Story scope is UI/flow enhancement on order screen footer: provide two actions to link order to invoice without returning to cart.
- Both invoice actions are constrained by existing order-to-invoice logic/validation; no new linking rules are defined.
- Add to New Invoice is disabled until all mandatory order fields are completed.
- Add to Existing Invoice is hidden when patient has no invoices in Open status.
- Clicking Add to Existing Invoice opens a dropdown above the button listing all Open invoices.
- Selecting an Open invoice links the order to that invoice and redirects user to invoice page.
- Clicking Add to New Invoice links order to newly created invoice and redirects user to invoice page.
- If opening an order already linked to an Open invoice, both link buttons are hidden.
- Eyeglasses orders must run makeability check before linking for either action, per GEM-28947 current rules.
- Applicability is explicitly PV only; wholesale behavior excluded and tracked separately.

3. Missing information
- Exact definition/list of 'mandatory order fields' is not provided in this ticket.
- No explicit expected behavior when Add to Existing Invoice dropdown has many items (sorting, pagination, search, truncation) is provided.
- No explicit UI text/error behavior defined for makeability check failure on eyeglasses in this story.
- No explicit permission/role constraints are defined for visibility/clickability of invoice actions.
- No explicit behavior defined if open-invoice list changes between dropdown open and selection (stale data/concurrency).
- No acceptance criteria provided for API/network failure during link/create-and-link actions.

4. Ambiguities
- Description states 'two invoice actions are available' and also says Add to Existing is hidden when no open invoices; wording could be interpreted as conditionally available.
- Global statement says both actions remain disabled until mandatory fields complete, but section behavior only explicitly disables Add to New Invoice; Add to Existing enable/disable state is unclear.
- Behavior when order is linked to a non-open invoice is not specified for button visibility.
- Whether dropdown should refresh open invoices on each click or use cached list is not specified.
- Redirect destination detail (invoice details page vs specific tab/section) is not specified.

5. Risks
- Inconsistent gating between Add to New and Add to Existing could allow invalid linking before required fields are complete.
- Incorrect visibility logic may expose Add to Existing when no open invoices, causing dead-end UX.
- Regression risk to existing cart-screen invoice linking flow and shared linking backend logic.
- Makeability check integration risk for eyeglasses could be bypassed or double-triggered.
- PV-only scope risk: accidental impact on wholesale if tenant/channel scoping is not enforced.
- Concurrency risk if selected open invoice becomes closed before linking is submitted.

6. Dependencies
- Existing order-to-invoice linking service/validation logic.
- Invoice status data source for patient invoices (Open status filtering).
- Eyeglasses makeability rules/process from GEM-28947.
- Order form mandatory-field validation logic.
- Navigation/routing to invoice page after successful link.
- Linked issue GEM-38725 (Ordering Testing) for broader testing coordination.

7. Clarification questions
- Should Add to Existing Invoice also be disabled until all mandatory fields are completed, or only Add to New Invoice?
- What are the exact mandatory order fields in PV context for this gating?
- If order is already linked to a non-open invoice, should the two buttons be shown or hidden?
- How should open invoices be ordered in dropdown (e.g., newest first, invoice number, due date)?
- What should user see when makeability check fails for eyeglasses (message text, blocking behavior, stay on order page)?
- What is expected behavior on API/network errors when creating/linking invoice (toast/modal, retry option, no redirect)?
- Are there role-based access rules for these actions that must be enforced/tested?
- Should dropdown list refresh at open time to reflect real-time invoice status changes?
